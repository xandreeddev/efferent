# @xandreed/plugin-agent-loop

The step loop: `runLoop`, a provider-agnostic loop over effect/ai's `LanguageModel` that sends a step, gates its response on its finish reason, runs its tool calls itself through the toolkit and iterates until the model stops, the step cap or the degenerate-loop breaker; and `runSteps`, core's `StepLoop` over it, which maps a turn's `StepRequest` (plan, record, events, completion, tasks, steering) onto the loop's callbacks. Node 24 and Bun; layer `plugin-agent-loop` in `foundry.config.ts` (imports core only).

## Rules

- Keep the decisions pure and tested alone: `foldProgress` (defaults: nudge at 3 stale steps, stop at 5) and `nextPhase` (the breaker, whether more work waits, then the step cap). `LoopLimits.degenerate` accepts `Enabled { nudgeAfter, breakAfter }` with positive bounded thresholds and the nudge before the stop, or `Disabled`; disabling never bypasses `maxSteps`. `foldProgress`'s optional third argument accepts the same policy; its two-argument behavior stays unchanged.
- Only the model's own unusable output (`InvalidOutputError` from the response's decoding, mostly a tool call's arguments that are not valid JSON; `ToolNotFoundError` and `ToolParameterValidationError`, which the loop makes from `malformedCall`, and which effect/ai's Anthropic and OpenAI adapters also raise for a call's arguments that are not valid JSON, before any finish part, a call a cut left unfinished included) gets a corrective turn, bounded by `LoopLimits.malformedLimit` (default 3: the third consecutive malformed response fails, so two correctives are tolerated); a provider's `InvalidResponseError` fails the step. Invalid thresholds fail with `config.options` before any provider dispatch.
- The loop runs a response's tool calls itself, and never lets the model call resolve them: it calls the model with `disableToolCallResolution: true` and `toolCallValidation: "deferred"`, mints the calls' ids (`withToolCallIds`), then gates on the finish reason (`verdictOf`). The calls that count are the loop's to run (tool-call parts with `providerExecuted !== true`); a provider-executed call is the provider's, never answered by the loop.
- The whole/cut split is declared once: `WholeReason` (`stop`, `tool-calls`, `pause`, picked from core's `FinishReason`) in `response-gate.entity.ts`, `CutReason` every other reason, and `verdictOf` tests membership with `Schema.is(WholeReason)`, no second list. `unknown` (the provider gave no finish reason) cuts a response only when it holds calls the loop would run (`verdictOf(reason, callsToRun)`); a reply in text, or an empty one, without a finish completes as a whole one does (the empty reply that says "done" after tool calls among them).
- Only a whole response whose every call passes `malformedCall` (a tool the step has, looked up as the tools' own key with `Object.hasOwn`, so `constructor` or `toString` names none; parameters that decode) runs its calls, each through the instrumented toolkit (`runCall`), at most `toolConcurrency` at once, their results in call order; when one call fails, none runs and the step is malformed. A cut response runs none of its calls and checks none: each is answered with `replyCutFailure`, the step settles `truncated` with no completion evaluated, and `recut` answers a `length` cut with `lengthCorrective` under the next step (its variant by whether the reply held calls the loop would run, `Responded.callsToRun`), at most `MAX_CUT_CORRECTIVES` in a row; any other cut, or one more, fails the run with `loop.truncated` (`truncatedMessage`, built with core's `harnessError`). A `pause` continues the run, and gets no completion corrective under `requireCompletion`: the next call continues the paused reply.
- The streaks reset each other: a whole response resets both, a malformed one (`recover`) the cuts in a row (`cutStreak`), a cut one (`recut`) the malformed ones in a row (`malformedStreak`).
- Persistence uses `onTail` incrementally: first the complete assistant response, then each settled result as it returns, before waiting for siblings. `assistant_message` is emitted after the first durable record and before handlers, so an interrupted step keeps its usage. The standalone loop's returned tail stays in call order; the journal records concurrent results in completion order. The final combined tail is never recorded twice. `StepRequest.record` returns only after storage; `TurnLive` flushes raw memory entries before optional digest-on-write work.
- A repeated executable call id is malformed before any handler runs: a pairing key must name one call. Its corrective is pinned exactly, like the other gate texts. A step's results come from `StepRequest.recorded`, a fresh durable snapshot, so failed presentation work cannot hide a stored raw result.
- `recut`'s continuing path makes the next step's input as `decide` does, through the one helper `nextInput`: the corrective recorded under the next step, then within-run compaction (`compact` over the next buffer with the cut step's usage, the plan's assistant-boundary check, the `compaction` event), then steering (`pendingInput`, after the fold, recorded under the next step).
- The run's text across a continuation: `LoopState.carried`. A reply in text cut at the output limit (no call the loop would run) and answered with the continue corrective, and a whole `pause` step the run goes on from, append their text to `carried`; the next step that is neither sets `finalText` to the carried text followed by its own when that is not empty (else keeps the previous `finalText`) and empties `carried` (`settledText`). A length cut whose reply held calls the loop would run is replied to anew, not carried. A run the step cap ends while text is carried has that text in its `finalText`; a malformed step neither carries nor ends a continuation, unless the cap ends the run there.
- A corrective turn counts against `maxSteps`, and the loop's appended messages (corrective, nudge, nondurable steering) go through `onTail` before the next call, under the next step, and only when that step runs: `onTail(messages, step)` records a step's own tail under it, nothing under it after it settled, and nothing under a step the run never takes (a run the step cap, the breaker or completion ends drops the corrective or nudge it would have sent).
- A step runs in two parts. It executes (the call, the tools, the tail), then settles: `onStepSettled(step, status)` runs exactly once, with that execution's exit (`completed`, `failed`, `cancelled`, `malformed` for a response the model could not form, or `truncated` for one cut short). Only then does the loop decide: `isComplete(step)` (a query, never asked after a malformed or a truncated step), the breaker, compaction, steering. A decision that fails fails the run, never the settled step.
- Durable input has a separate `durableInput` probe/take pair (`StepRequest.pendingSteers` and `steer(step)`). `beginStep` publishes `step.started`, then takes exact queued user messages before planning or dispatch, including step zero. Returned messages are already durable: add them to the standalone buffer/tail without passing them through `onTail` again.
- Probe durable steering after settlement, after the host's completion verdict for whole replies, final replies included. Waiting input requests continuation when hard limits permit; the step cap or breaker leaves it queued and records nothing under a nonexistent next step. A final empty probe is the completion boundary: arrivals after it wait for another turn. A failed take prevents dispatch and fails its started step. Keep nondurable `pendingInput` on its existing continuing path after compaction.
- `runSteps` publishes `step.ended` from `onStepSettled` and nowhere else, reading its result entries from `StepRequest.recorded` in durable journal order, including on failure. What it carries across steps is one `Ref<StepLedger>` (the plan cache, the last usage, the steps started), updated by the pure functions of `step-ledger.entity.functions.ts`. It returns `RunResult`'s union (`completed`/`completed`, or `partial` with `step-cap` or `degenerate-loop`).
- Progress is keyed on results, not arguments, and pollable tools never count toward the breaker.
- A stream that fails before its first part falls back to `generateText` for the rest of the run with one `stream_fallback`; once a part arrived, a failure fails the step.
- A request refused over an image is sent again only before any part arrived, and only when `onMediaRejected` dealt with the images.
- Step spans carry a call's usage under the GenAI names and the run span the sum under `engine.usage.*`; content only with `captureTraceContent`, images by size. Each tool call the loop runs has its own span under its step's, `loop.tool_call` (attributes `engine.tool`, `engine.tool.call_id`), around its handle and its drain (`runCall`), so the handler's spans nest under it. effect/ai's toolkit annotates the span current where a call is handled with the call's `tool` and `parameters`: they land on the call's own span, one call's never over another's, and never on the step's (on the call's whatever `captureTraceContent` says, as they landed on effect/ai's model-call span when it ran the calls).
- `runSteps` computes a step's plan once and serves the model, the messages and the tool choice from it.
- The loop provides core's `StepLoopReferences`, whatever the caller's: `runSteps` the request's `cacheKey` and `callPolicy` for the run, `runLoop` its exact `CurrentAgentRun` and `captureTraceContent` for the run and the step and the empty-response tolerance per step. A standalone `runLoop` without a run provides `None`. Its callbacks run with the caller's services, never with the caller's run, step or tolerance (an outer run's). The request's `handlers` hold the turn's services, the caller's values of those references included, so `runSteps` provides `handlers` outermost and its own references inside them. Concurrent runs keep distinct ordinals through Toolkit's child handler fibers.
- `runLoop`'s callbacks fail with the caller's error (`RunLoopOptions<Tools, E, R>`), and the run fails with `E | AiError | HarnessError`: the caller's `E`, a provider's `AiError`, or the loop's own `loop.truncated` (a reply cut short the loop does not answer): a callback that can fail returns its failure, never `Effect.orDie`s it.
- `runSteps` fails with a turn's `TurnError` as it is (`isTurnError`: the writer's `TurnClosed` keeps its tag, and the loop's `loop.truncated`, a `HarnessError`, its code), and with anything else (a provider's `AiError`) as `loop.failed`, that failure its `cause` and its messages without its tag (`messagesOf`) the message, which a background task's notice may show the model. The request's callbacks reach `runLoop` as `E = TurnError`; `harnessDefectsAsFailures` stays only for a tool handler's `TurnError`, which its `never` error channel carries as a defect.
- The default corrective texts are model-facing: a host's `correctives` replaces them, and a change to them updates their pins. The gate's texts (`replyCutFailure`, `lengthCorrective`) are the loop's own: no host text replaces them, and they are pinned the same way.

## Public surface

- `runLoop` with its types (`RunLoopOptions`, `CompactionPlan`, `StepView`, `LoopToolChoice`, `Phase`), `foldProgress`, `nextPhase`, `DEFAULT_MAX_STEPS`, `DEFAULT_TOOL_CONCURRENCY`, `DEGENERATE_REPEAT_NUDGE`, `DEGENERATE_LOOP_STOP` (`src/loop.ts`).
- `stepLoopPlugin` (also the default export), `StepLoopLive`, `runSteps`, `STEP_LOOP` (`src/step-loop.adapter.ts`).
- `LoopEvent`, the loop's event vocabulary: what `runLoop` hands its `onEvent` sink, and what `runSteps` turns into the turn's events (`src/loop-event.entity.ts`).

The root names each export, and `quality/exports-have-consumers` checks each one: other packages' tests, the scripts and the docs import `stepLoopPlugin`, `StepLoopLive` and `runSteps`, and the rest, which no first-party package imports, are tagged `@public` at their declarations (`stepLoopPlugin`'s tag covers the default export).
