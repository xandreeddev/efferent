<Step n={1} id="build" title="What you will build" focus="code">

Some answers are better shown than said: a table of results, a card, the progress of slow work. This lesson's agent gets a tool, `show`, that puts a table in the chat.

What is shown belongs to the UI, never to the model. A table costs its size in every later request if it is sent as text. So `show` stores the table as a **view**: a record of its own in the journal, tagged `ui`. The chat draws it, and no memory sends it. The model reads only a few words: "shown as squares".

One rule makes it work: **the model asks, the tool makes**. What the model writes in a call is its own message, stored and sent with the conversation. So the model asks in a few words, "the squares to 5", and the tool works out the rows.

</Step>

<Step n={2} id="model" title="Pick a model" focus="model">

This lesson runs on **Echo**. "Show a table of squares to 5" or "show the times table of 7" goes to `show`, by rule.

The small models on your machine rarely call a tool, as lesson 2 showed. Hosted models use `show` when their system text tells them to.

</Step>

<Step n={3} id="tool" title="A tool that shows" focus="code" file="tools">

**tools.ts** declares `show`. It takes three small things: an `id`, which `table` (`squares`, `cubes` or `times`) and `n`. The **id is the model's**: showing again under the same id replaces the table, keeping its place in the chat. The rows are the handler's own work, from `kinds`.

Its handler needs one thing, which it lists in `dependencies`: **`CurrentTurn`**, the turn its call runs in. Through it the handler does two things:

- it `append`s the view, which is stored;
- it `publish`es progress as it goes, which is live and stored nowhere.

A call the model gets wrong, such as `n` of 50, is a failure the model reads, and nothing is shown.

</Step>

<Step n={4} id="loop" title="The loop gives each call its turn" focus="code" file="agent">

**agent.ts** is lesson 2's program on the kernel's `modelAnswer` and `callTool`, with a system text that names `show`. Its loop runs each call with `callTool(toolkit, call, session)`. The loop holds the open turn, and `callTool` gives each call its turn: a tool that declares `CurrentTurn` always has it, and a tool that declares nothing never notices. There is no line here to forget.

</Step>

<Step n={5} id="watch" title="Watch it" focus="context" wide={true}>

Ask **"Show a table of squares to 5"**. The table appears in the chat. Then ask for squares to 8: the same table updates in its place.

Open **Context**:

- **Journal**: between the call and its result, a record `plugin.render.view`, tagged `ui`. Its payload is the view.
- **Memory**: the view is not there. It is not conversation, and memory skips it.
- **Prompt**: the call, `show({ id, table, n })`, and the result "shown as squares". None of the cells.

The chat draws views by folding the journal: one view per id, the latest wins. The button below forgets everything the chat drew and draws it again from the journal alone, as a reload would: every stored message, tool result and view comes back where it was.

</Step>
