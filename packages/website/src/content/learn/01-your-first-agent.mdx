<Step n={1} id="build" title="What you will build" focus="code">

An Efferent agent is not one big class. It is a handful of **plugins**, each with one job, that `Agent.define` checks and joins into one agent.

Yours needs three: one to **remember** the conversation, one to **find tools** (none yet, but the loop expects a registry), and the **loop** that asks the model for an answer.

Everything here is the real framework running in your browser. The code on the right is the whole agent: three plugins and one `Agent.define` call.

</Step>

<Step n={2} id="model" title="Pick a model" focus="model">

Open the **Model** list above. **Echo** needs no download and answers only from the messages it is sent, which is ideal for seeing what your agent remembers.

For real answers use a model on your own machine; nothing you type leaves your browser.

- **CPU models** work anywhere, but are small: expect odd answers.
- **GPU models** (WebLLM, Phi-3.5 mini included) and **Chrome's built-in model** need WebGPU or a recent Chrome. If yours cannot run them, the list says why.

</Step>

<Step n={3} id="code" title="The agent in a few lines" focus="code">

The **Code** pane is the whole program. The grey chips (imports, session, run a turn) are read-only; click one to open it.

You edit the object passed to `Agent.define`:

- **`system`**: instructions the model sees on every request.
- **`plugins`**: what the agent is made of; `{ plugin, options }` configures one.
- **`limits`**: `maxSteps` model calls per run; `streaming` shows the reply as it arrives.
- **`budgetTokens`**: how much context memory may send per request.

Press **Rebuild** (Ctrl/Cmd + Enter) to see what `Agent.define` accepted, or why it refused.

</Step>

<Step n={4} id="chat" title="Talk to it" focus="chat">

Say something in the **Chat** pane, then ask **"What did I just say?"**. The second turn can answer because the memory plugin gives the model the first one.

A turn is one message in and one reply out: `agent.turn` runs the loop until the model has answered. **Stop** interrupts a reply.

**Clear context** wipes the chat and the conversation behind it. A rebuild keeps the conversation unless you untick **Keep chat on rebuild**.

</Step>

<Step n={5} id="loop" title="The loop, step by step" focus="context" view="loop">

Send a message and watch the **Loop** view: each highlight is a real event.

1. Memory **builds the context** (`context.built`).
2. The loop **calls the model** (`assistant.delta`).
3. It **records the answer** (`assistant.message`, `step.ended`).
4. It **decides whether to go again** (`completion.evaluated`). A reply with no tool calls ends the run.

With tools, a step can end with "run this tool" and the loop goes around again. That is lesson 2.

</Step>

<Step n={6} id="context" title="Context: the journal and the memory window" focus="context" view="inspector" unfold="session" wide="true">

Every message goes into the **journal**: an append-only record that is never edited. The **memory window** plugin then decides which of it the model sees on each request. The session setup in the Code pane is where the journal lives.

<p class="learn-try"><button class="btn btn-primary" type="button" data-fill>Send 5 short messages</button></p>

Then drag **Budget** down to about 350 and **send another message**: the budget applies to the next request. Older turns leave the **stack** and become a ledger note; the **journal** keeps them.

The green bar marks what matches the previous request: all a provider's prompt cache could reuse. It shrinks when older turns are rewritten.

Too low and the window refuses: the system prompt, the ledger note and your current message must all fit, and the ledger grows with every dropped turn. The chat then offers to raise the budget or clear the context. Each dropped turn costs up to 480 characters in the ledger (`ledgerTurnChars`, 240 per message and reply, is an option of `memoryWindowPlugin`), so a real model's long replies reach the limit sooner than Echo's short ones.

</Step>

<Step n={7} id="tiny" title="Write a memory plugin" focus="code" file="tiny" view="inspector">

A memory strategy is just a plugin that provides `ConversationMemory`. The **tiny-memory.ts** file is a complete one in about 60 lines (the **Format** button tidies whatever you change): it keeps the last *n* turns and replaces older ones with a ledger note.

<p class="learn-try"><button class="btn btn-primary" type="button" data-exp="tiny-swap">Swap in tinyMemory(2)</button> <button class="btn" type="button" data-exp="window-swap">Swap the window back</button></p>

Swapping starts a new conversation here, so you compare both strategies from the same starting point. Send five messages and compare the stack with the window's. Unlike the window, this plugin never looks at the budget: it keeps a fixed number of turns, even if that goes over.

Edit the plugin (try `ledgerOf(entries, dropThrough, 10)`) and rebuild. Use ⤢ on the Context pane for the full picture.

</Step>
