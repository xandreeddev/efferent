<Step n={1} id="build" title="What you will build" focus="code">

An agent is a program: it takes your messages one by one and answers each in a **turn**. You write that program in **agent.ts**, on the right. It is the whole agent: no loop hides behind it.

It stands on a small **kernel**: events every part can hook, a **journal** that stores the conversation, and **sessions**, which open and close turns. Next to the kernel are **modules**, each with one job: the **chat** your messages come from, a **memory** that picks what the model sees, and the **model**.

It works like Neovim. The kernel is the editor's core, the modules are plugins, and your program is `init.lua`, which sets them up and wires them together:

| In Neovim | Here |
|---|---|
| plugins set up on start | modules given to `main` with `Effect.provide` |
| an autocmd on an event | `core.on(turnStartedEvent, …)` on boot |
| a key mapping that calls a plugin | a message arrives, and `turn` calls memory and the model |

Everything runs in your browser.

</Step>

<Step n={2} id="model" title="Pick a model" focus="model">

Open the **Model** list above. **Echo** needs no download and answers only from the messages it is sent, which is ideal for seeing what your agent remembers.

For real answers use a model on your own machine; nothing you type leaves your browser.

- **CPU models** work anywhere, but are small: expect odd answers.
- **GPU models** (WebLLM, Phi-3.5 mini included) and **Chrome's built-in model** need WebGPU or a recent Chrome. If yours cannot run them, the list says why.

</Step>

<Step n={3} id="program" title="The program" focus="code">

Read **agent.ts** from the bottom up.

**`main`** gives `program` the modules it asks for. Each `Effect.provide` adds one: `flatMemory` from memory.ts, the chat over this page's pane, sessions, the journal, the kernel and the model you picked. If one is missing, the program stops the first time it asks for it.

**`program`** runs as long as the page is open. On boot it hooks an event: when a turn starts, it sets the chat's status line (above the chat). Then it takes each message from `chat.messages` and runs **`turn`** on it, one at a time, so a message sent mid-turn waits for its own. A failed turn is shown in the chat, and the program goes on.

**chat.ts** (read-only) is where messages come from: Send puts yours on a queue, and `chat.messages` hands them over.

**Rebuild** (Ctrl/Cmd + Enter) stops your program and runs the code again. The conversation stays: the journal and the chat's queue are built once, under your program. A turn that was running ends **Interrupted**. Messages still waiting are kept.

</Step>

<Step n={4} id="turn" title="One turn" focus="context">

Send a message and watch the **Context** tab. It has replaced the code: the tabs at the top of the Code pane switch back. The seven boxes are the lines of `turn`, lit as they run:

1. **Open a turn**: `sessions.open(chat.session)`. The turn is a scope: it closes when the scope ends, answered, failed or stopped, and records how.
2. **Store your message**: `session.append(userMessage(message))`. It is in the journal before the model sees anything.
3. **Ask memory for the context**: `memory.context(session)` reads the journal and returns the messages the model will see.
4. **Build the prompt and call the model**: the **system text** first, then the context. The system text is code: it is never stored, so changing it changes the next prompt and nothing goes stale.
5. **Stream** each piece of the answer to the chat.
6. **Store the answer**, so the next turn's context has it.
7. **The turn closes.**

Click a box: what it wrote or read lights up below. Hover a row in one column and the same record lights up in the others. **▶ Replay** walks through the steps again.

The **journal** holds the conversation and nothing derived: turn records, your messages and the answers, each with its sequence number, its turn and its **tags**. Memory reads only records tagged `conversation`. Click a record to see what is stored.

</Step>

<Step n={5} id="queue" title="Many messages" focus="chat">

Press **Send three at once**. All three wait in the queue (marked *waiting*), and the program takes them one by one: each gets a turn of its own, in order, and each turn's context has the turns before it.

Send a message while an answer is streaming: it waits for its own turn. In later lessons a turn runs many steps, and a message sent mid-turn becomes a way to steer it.

**Stop** stops the running turn, drops the waiting messages and runs your program again. **Clear context** starts a new, empty conversation; the old one stays in the journal store.

</Step>

<Step n={6} id="context" title="Context and the cache" focus="context" wide={true}>

<p class="learn-try"><button class="btn btn-primary" type="button" data-fill>Send 5 short messages</button></p>

Pick a turn at the top. The **Prompt** column shows where each message came from: *your code* for the system text, *memory* with the record it came from. Every prompt is built fresh.

The green bar is the part of the prompt that is the same as the one before, from the start. That is what a hosted provider's **prompt cache** can reuse, so you pay less and wait less. With flat memory each prompt starts with the one before it, so the bar grows turn after turn. Local models have no cache, so the counts here are the kernel's estimate: a quarter of the characters.

The **events log** at the bottom lists everything in order: each record as it is stored, what memory gave, each prompt, and what your program told the chat.

</Step>

<Step n={7} id="memory" title="Write a memory" focus="code" file="memory">

A memory is a layer that provides `Memory`, with one function: `context(session)`, the messages the model sees after the system text. **memory.ts** is yours. This one is flat: every message of the conversation, oldest first.

It reads with a **reader**, which takes the records tagged `conversation`, refuses one it cannot read and may not skip, and passes over the rest. `messageOf` turns a record into a message, and `promptMessage` into what a prompt sends.

<p class="learn-try"><button class="btn btn-primary" type="button" data-exp="last-two">Keep only the last two messages</button></p>

That adds `.slice(-2)`. Send a few messages and open the **Context** tab: older records are now **left out by memory** (struck through), though the journal keeps them all. Ask "What did I just say?" a few turns later: Echo can no longer see it.

Now look at the green bar: only the system text is the same as the prompt before, because the window slides every turn and the start of the prompt moves. A memory that drops messages breaks the cache on every request. Better memories (a window that drops whole turns rarely, a summary, pointers the model can recall) are the next lessons.

The kit that checks the stock memories checks yours too (`memoryConformance`): flat memory passes every check.

</Step>
