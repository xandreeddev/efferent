<Step n={1} id="build" title="What you will build" focus="code">

An Efferent agent is not one big class. It is a stack of small parts, each an Effect `Layer` with one job.

At the bottom is a small **kernel**: events, a journal that records the conversation, and sessions. On top you put the parts of an agent: an **inbox** that queues your messages, the **loop** that asks the model, a **memory** that decides what the model is sent, and the **system text**.

Everything here runs in your browser. The code on the right is the whole program.

</Step>

<Step n={2} id="model" title="Pick a model" focus="model">

Open the **Model** list above. **Echo** needs no download and answers only from the messages it is sent, which is ideal for seeing what your agent remembers.

For real answers use a model on your own machine; nothing you type leaves your browser.

- **CPU models** work anywhere, but are small: expect odd answers.
- **GPU models** (WebLLM, Phi-3.5 mini included) and **Chrome's built-in model** need WebGPU or a recent Chrome. If yours cannot run them, the list says why.

</Step>

<Step n={3} id="code" title="The agent in a few lines" focus="code">

The **Code** pane is the whole program. The grey chips (imports, the base, run) are read-only; click one to open it.

The **base** is built once: the kernel's events, a journal kept in memory, and sessions. The conversation lives there.

You edit the **agent**, the layers above the base:

- **`inbox`**: queues each message and answers them in order, one turn each.
- **`stepLoop`**: the loop. It stores your message, asks memory for a request, calls the model and stores the answer.
- **`windowMemory({ budgetTokens })`**: decides what each request sends, within a budget of tokens.
- **`settings({ system })`**: the system text the loop and memory read.

Each part says in its type what it needs. `Layer.provideMerge` puts a part under the one above it, so the stack reads from the top down and is built from the bottom up.

Press **Rebuild** (Ctrl/Cmd + Enter). The page closes the old agent and builds yours over the same base, or says why it could not.

</Step>

<Step n={4} id="chat" title="Talk to it" focus="chat">

Say something in the **Chat** pane, then ask **"What did I just say?"**. The second turn can answer because memory sends the model the first one.

Messages go through the inbox. Press **Send three at once**: all three are queued before the first is answered. Each gets a ticket, then a turn of its own, in order, and each turn sees the turns before it.

**Stop** ends the turn that is running and drops the messages still waiting. The page then builds the agent again.

**Clear context** starts a new, empty session. A rebuild keeps the conversation, because it lives in the base. Untick **Keep chat on rebuild** to start a new one on every rebuild.

</Step>

<Step n={5} id="loop" title="The loop, step by step" focus="context" view="loop">

Send a message and watch the **Loop** view. Each row is a kernel event the page heard on `Core`; the pieces of one answer share a row.

1. The inbox **queues** your message (`plugin.inbox.queued`).
2. A **turn** opens (`core.session.turn.started`), and the loop stores your message (`plugin.loop.user.message`).
3. Memory **builds the request**, and the loop stores it before the call (`plugin.loop.request.sent`). Its messages are pointers into the journal, not copies.
4. The model **answers** piece by piece (`plugin.loop.assistant.delta`), and the loop stores the whole answer (`plugin.loop.assistant.message`).
5. The turn **closes** (`core.session.turn.ended`), with how it ended.

With tools, the loop would go around again after step 4. That is lesson 2.

</Step>

<Step n={6} id="context" title="Context: the journal and memory" focus="context" view="inspector" unfold="base" wide="true">

Every message goes into the **journal**: an append-only record that is never edited. **Memory** then decides which of it the model sees on each request. The base in the Code pane is where the journal lives.

<p class="learn-try"><button class="btn btn-primary" type="button" data-fill>Send 5 short messages</button></p>

They are queued at once and answered in order. With Echo, each turn costs about 24 tokens and the system text 12, so five turns fit easily in 3000.

Then drag **Budget** down to about 80 and **send another message**: the budget applies to the next request. Whole turns leave the **stack**, oldest first, until the request fits. The **journal** keeps them, and the window records what it dropped (`plugin.window.dropped`). A turn once dropped stays dropped.

The green bar marks what matches the previous request: all a provider's prompt cache could reuse. While nothing is dropped, each request starts with the one before it, so the bar grows. The request that drops turns starts elsewhere: only the system text matches the one before it.

Too low and memory refuses. It always sends the system text and the message the turn answers, and drops only older turns. If those two alone are over the budget, the turn fails with `OverBudget` and no request is sent. The chat says so and offers to raise the budget. A real model's longer replies fill the budget sooner than Echo's short ones.

</Step>

<Step n={7} id="tiny" title="Write a memory" focus="code" file="tiny" view="inspector">

A memory is a layer that provides `Memory`. Its one function, `build`, reads the journal and returns pointers to the messages to send, with an estimate and the budget. The function you edit in **tiny-memory.ts** is a whole one in under 50 lines (the **Format** button tidies whatever you change): `lastMessages` sends the last *n* messages, fewer if they do not fit the budget.

<p class="learn-try"><button class="btn btn-primary" type="button" data-exp="last-memory">Swap in lastMessages</button> <button class="btn" type="button" data-exp="window-memory">Swap the window back</button></p>

The swap sets `n: 1`: the model sees only your newest message. Ask "What did I just say?" and Echo has nothing earlier to recall. The journal still holds everything, so with the window back the next request sends the conversation again, within its budget.

Change `n` to 3 in agent.ts and rebuild: the model sees the last three messages, yours and its answers.

The kit that checks the stock memory checks yours too (`memoryConformance`). It passes every check but one: `prefix`. While nothing presses, a request should start with the one before it, so a provider can reuse its cache. Once it starts leaving messages out, a sliding memory moves the start of each request, so nothing after the system text can be reused. The green bar shows it. Use ⤢ on the Context pane for the full picture.

</Step>
