# @xandreed/review

`efferent-review`, a pull request reviewer built on the kernel: it reads a pull request from its forge, its diff, the repository's rules and its CI, prepares them for a review, and reviews it with a model. `efferent-review prepare <number> --repo <owner/name>` prints what a review is given, asking no model; `efferent-review review <number> --repo <owner/name>` runs several turns of the model over it, merges what they find, checks each finding with the model and prints the report. With `--run <command>` or `--validate`, either also runs the pull request's commands in bubblewrap sandboxes ("The sandbox" below). Node 24 (the declared engine; the tests run on Bun): the package is not built, so the bin, `bin/efferent-review.mjs`, loads `src/main.ts` through `tsx`; layer `review` in `foundry.config.ts` (imports `@xandreed/core`, `@xandreed/sdk`, `@xandreed/sdk/node`, `effect/ai` and `node:` only). Private: it is gated like every package, but it is in neither the build's `names` nor `CURATED_ENTRIES`, and Changesets ignores it (`.changeset/config.json`, `ignoredNames` in `scripts/release-version-plan.ts`), so no release publishes it.

## Rules

- The orchestration is code, never a model: fetching, filtering, packing, running and digesting are pure functions with table tests (`*.entity.functions.ts`) or adapters behind a port.
- Every host command whose output is parsed (`gh … --json`, `gh api`, `git diff`, `git ls-tree`, `git cat-file`, `gh run view --log-failed`) is read whole through `runWhole`: the host's shell keeps `HOST_OUTPUT_BYTES` of each stream, and an output it cut fails with `OutputCut`, never parsed. An exit code the caller did not allow is `CommandFailed`.
- Every argument of a host command is quoted (`commandLine`): a path, a branch or a title from a pull request is data, never shell.
- A pull request's rules are read at the base of the commit under review (`show` at `at.base`), so it cannot rewrite the rules it is reviewed by; a link (`CLAUDE.md` → `AGENTS.md`) is not read twice.
- `gh` and `git` run on the host's shell with the host's environment (`gh` reads its login there). Nothing of the pull request's runs on the host: a process of the host's user can read the parent's environment (`/proc/<pid>/environ`), the host's credentials and the shared clone, whatever variables it is given, so trimming the environment is no isolation. A pull request's commands run only through `Validations` (`sandboxValidations`, in bubblewrap sandboxes, "The sandbox" below); the command line provides it only for `--run` or `--validate`, and fails with `SandboxUnavailable` on a host that cannot make a sandbox. `prepareReview` runs commands only for a head in the base repository whose author may write to it (`admin`, `maintain` or `write`); each clone's shell runs only its listed commands (`allowOnly`, a guard on which commands run, not isolation). CI's failed logs stay the first validation source. The commands run on the commit under review and its base (`at`).
- Every host-side git command is built by `gitArgv`: `core.hooksPath=/dev/null` (no hook of the clone's runs), `core.fsmonitor=false`, `core.attributesFile=/dev/null` and git-lfs's filters emptied (no filter of the host's runs on a pull request's files), `protocol.allow=never` with only the transports given allowed (`https` by default), and `--literal-pathspecs` (a folder named `:(glob)x` or `:!x` is a name).
- Clones live under a cache root outside every git repository (`~/.efferent-review/<owner>/<repo>/` by default; `CacheRootRefused` otherwise): a bare clone in `mirror.git`, worktrees in `worktrees/`, removed when their scope closes. What the sandboxes use is beside them (`directoryCache`): a throwaway clone per run in `clones/` (`Checkout.clone`), the bot's package cache of each manager in `packages/<manager>/`, each command's verdict on the base in `verdicts/`, snapshots of the base's `node_modules` in `node-modules/`, and folders thrown away after a run in `scratch/`. Logs and records live under a records root of their own (`--records`, `~/.efferent-review/records/<owner>/<repo>/` by default), in `<number>/<sha>/` (the commit under review, its full sha), each run's records in a folder of its own in it, made only when nothing is there (`ReviewLogs.fresh`); every log and record is written whole or not at all (a temporary file renamed over it); nothing cleans them, so a review's records are never lost with a clone.
- CI runs are every run for the reviewed commit's sha started by `pull_request`, `push`, `merge_group` or `pull_request_target` (`CI_EVENTS`), every page of runs and of jobs read (`gh api --paginate --slurp`); a run with no job is not listed. A failed log the forge no longer has is `NoLog`; one it refuses (auth, a repository 404) is that run's `Unavailable` entry, stripped and cut, and fails nothing else.
- Everything a log, a path or a title holds is the pull request's text. A digest strips escape sequences and control characters, cuts each line with the kernel's `clipTo` and bounds its failures and summary; a path is shown through `shownPath` (a JSON string when it holds a control character, a quote or a backslash), so a name cannot forge a line and maps back to one file.
- Which files the model reads: lockfiles, files the base's `.gitattributes` marks generated or vendored (a folder's name drops nothing), binary and deleted files are left out, each named in a line with its counts (a lockfile with whether a manifest changed too); a file that only loses lines is kept. The rest is packed manifests, CI files and small config first (smallest first), then the source in git's order (`PackRanking` `git`; `largest` puts it largest first), then tests, then large config, then pages and docs (`isPageOrDocs`: docs, `.astro`, a `pages` or `docs` folder), each largest first. On the 36 tuning gold cases at 24,000 tokens it packs the defect's file in 28 (all of a case's in 17), against 25 (13) largest first and 21 (8) for the earlier code-largest-first packing.
- A focused review (`focus` `groups`, `DEFAULT_FOCUS`; `--focus whole` for the turns over the whole pull request) groups the changed code files (`isGrouped`: `fileKind` code, tests, pages, a docs folder's code and `.astro` files included; `groupFiles`, a policy, `ReviewPolicies.group`): by package (the nearest folder holding a `package.json` at the commit under review, looked up through `Checkout`), a package within `GroupBounds` (`DEFAULT_GROUP_BOUNDS`: 6,000 tokens of diff, 8 files) one group, a larger one cut into units of one stem in one folder (`charge.adapter.ts` with `charge.adapter.test.ts`; a test in a `test` folder with its source's stem) filled in order to the bounds, a file over them alone; groups with source first, then tests alone; run by risk (`orderGroups`, `GroupOptions.order` `risk`, `--group-order git` keeps git's order): source groups, then tests-only groups, then the config group, each tier riskiest first, ties in git's order; `riskOf` counts added lines holding a word of shared state, concurrency, processes, files, the network or secrets (`Ref`, `fork`, `scope`, `spawn`, `open(`, `umask`, `token`, `lock`, `retry`, `stream`…), four for source and one for a test, and a hundredth a source line; on the 36 tuning gold cases the first group holding a gold file comes at 5.2 on average (8.4 in git's order) and within the first seven in 28 (26). Config, manifests, lockfiles and docs get no turn unless `--config-turn` (one group more, last); each file no group holds is listed with why (`ungroupedOf`, `In no group:`). With no group at all (a pull request of config, CI or docs) the review falls back to the whole focus and notes it (`NO_GROUP_NOTE`). A `package.json` lookup that fails is noted (`lookupFailedNote`), its files grouped as if it held none. One turn a group, one after another (`DEFAULT_GROUP_STEPS`, 24 calls, `--group-steps`: a guard against a turn that never ends, the find stage's ledger being the real limit; measured on four gold groups, at 8 every turn hit the cap after reading across the whole pull request, at 24 every turn ended on its own after 5 to 17 calls), each keeping its closing reserve back (`DEFAULT_GROUP_RESERVE`, $0.10, at most half the find stage: a late request of a 24-call turn held $0.077); a group starts only while the find stage has that reserve and its first call's hold (`firstCallHold`: `firstCallBytes`, the messages as JSON as the ledger counts the body, `REQUEST_SLACK_BYTES` for the six tools and a host's tools' declaration bytes (`ReviewTurns.hostTools.declarationBytes`), at the input price, `maxOutputTokens` at the output price, from `ReviewOptions.price`) neither settled nor held, so a turn that starts can always close and report, else it and the rest are recorded as not reviewed (`NOT_REVIEWED_BECAUSE.spent`). A group's turn asks its first call once more after a failure worth another try (`TurnInput.retryFirstCall`); a refused turn that answered a call does not stop the next; a turn none of whose calls answered reviewed nothing (`noCallWhy`: `noCall` and how it ended): when the stage refused it the rest are recorded as `stopped`, after any other failure the next group runs. At about $0.022 to $0.053 a group (the 24-call guard and the harvest call), the stock find stage ($0.50) reviews about eight or nine groups (#644 at its first head: nine groups settled $0.39, and the ninth was refused part-way, since holds grow with every file read whole): a large pull request is cut short, its later groups listed. `--turns`, `--max-steps` and `--vote` (a group is reviewed by one turn, so a vote would count turns that wandered into another group's files, not agreement) are refused with `--focus groups`, `--group-steps`, `--group-order` and `--config-turn` with `--focus whole`; `--find-cost` or `--verify-cost` over `--max-cost` is refused, never clamped. A check on the prefix of a group whose turn never answered has no cache to read, and the report notes it (`uncachedCheckNote`). Each turn's prefix (`focusPrefix`) is three messages: the system text; one message with the rules, the title and description, every changed file (`filesText`, the first `FILES_SHOWN` (200) named and the rest counted, in place of the packed diff, so it is the same for every group) and the CI's digest; and the group's diffs (`GROUP_INTRO`, `files-under-review`); its tail is its finder's focused words alone (`FOCUS_TAIL`, `focusPrompt`): review the files under review, the other changed files being other turns', read each whole, ask for reads that do not depend on each other at once, and hold the description's claims against the code; what to look for and leave out is its finder's, as in `FIND_TAIL`. A check runs on the prefix of the group holding its finding's file (else of the group whose turn reported it), so its request starts with that turn's three messages byte for byte. The report keeps each group with its turn or why it was not reviewed (`GroupRun`).
- A stage's reasoning effort (`--effort-find`, `--effort-check`, `Effort`, recorded in `review.json`): `default` sends nothing; `none` sends the gateway's `reasoning: { enabled: false }`; the others `reasoning: { effort }` (`withEffort`); the checks get a model of their own (`KernelTurnsOptions.verifyModel`). Measured on DeepSeek V4.1 Flash on Baseten: only `none` changed anything seen (reasoning from about 3,000 tokens a call to 0, and a prompt template 25 tokens shorter, so its requests likely share no cache with default ones: not measured), and on #644's gold group it lost the defect the default found; `low` showed no change, possibly at a ceiling (every long probe call reasoned about 3,014 tokens).
- Every policy is swappable: `prepareReview(repo, number, options, policies)` takes `ReviewPolicies` (`verdict`, `pack`, `rulesAlong`, `digest`, `mayRun`, `failed`), `STOCK_POLICIES` by default; the head is fetched by the ref the forge serves it under (`fetchRef`).
- A review (`reviewPullRequest`) finds, merges and checks. Find: `turns` turns (`DEFAULT_TURNS`, 1, until an evaluation shows more find more; `--turns`), the first alone until its first model call returns (so the others may read the shared prefix from the provider's cache, which is not certain: on #645 at its first head the second turn's first call read 97% of its prompt from it, the third's 51%, and on a smaller pull request one read none; `TurnInput.onFirstAnswer` says whether that call answered, and is given `false` when the first turn ends or cannot run before one returned: then no other turn starts, and the report says so; that call is asked once more after a failure worth another try, `retryable`: a rate limit, a provider's error, a lost connection), then the others beside it; a turn or a check that cannot run at all (its folder not made, a defect) is a result that ended `Failed`, never a failed review; each walks the changed files in its own order (`walkOrders`: the files the packed diff shows and those it left out for the budget alone, grouped code, tests, manifests and config, docs, each largest first and dealt to the turns like cards, so turn `p` starts with every `K`-th file from the `p`-th) under the tail of its `finder` (`candidates` by default, `strict`). Merge: `mergeFindings`, pure, every finding into a `Bucket` by place (one file; a finding joins the first bucket whose anchor, its first finding, it starts within `NEAR_LINES` of and that holds no finding of its turn, so buckets never chain and one turn never votes twice; kinds share a bucket, whose kind is its best finding's; each finding's lines counted at most `SPAN_COUNTED`; votes its findings; the best-worded finding, the one its first check is shown, the most severe, then among those the longest evidence the file's diff holds, else the first (on #644 the gold leak, reported medium, shared a bucket with a low reading of the same lines whose evidence was longer, and only the low one was checked); a finding more than `CHANGED_SLACK` lines from a changed line bucketed apart as `off-changed-lines`); with the vote off (the default) every other bucket is kept, with it on (`--vote`) one of two votes or holding a `security` finding, the rest `one-vote`; every bucket is recorded. Check (unless `--no-verify`): one check per finding of a kept bucket, at most `CLAIMS_CHECKED` (3) a bucket, in rounds (`checkRounds`): every bucket's best first (`CHECK_ORDER`), then each bucket's next (the more severe, then in turn order) only for a bucket no check has confirmed (on #644's full run the gold leak was a bucket's second finding and was never checked; a defect several turns reported gets up to three tries and one confirmation reports it, which, with verdicts that flip between draws, trades precision for recall, not yet measured), `verifyConcurrency` at once within a round; only a confirmed finding is reported, a bucket once, with its first confirmed finding; each a turn of stage `Verify` on the same prefix, capped at `verifySteps` (`DEFAULT_VERIFY_STEPS`, 12: at 6, checks that read four or five files reached it), ending once `verdict` is recorded; a confirmed verdict whose quote is not in the head's file near the lines the check was shown (`quoteWithin`: the quote held by the cited lines, at most `SPAN_COUNTED` from the first whatever `endLine` says, and `QUOTE_SLACK` around them, whitespace and a tool's line numbers taken off; and one quoted line a whole line of the cited lines themselves (`CITED_SLACK`, one either side, for a numbering off by one) with `QUOTE_LINE_CHARS` characters and a name, so a brace, a `return` or a generic line around them proves nothing) is `unsure`, and a check with no verdict `unchecked` with why. Only confirmed findings are reported. `review.json` is kept as the review runs (`complete` false) and replaced once each stage ends; the run is named by its start and six random hexadecimal digits. `Findings` keeps each run's findings and verdicts under the run (`Reviewed.run`), so a store a host reuses never mixes two runs.
- A turn (a finder's, or a check's: the kernel's word, each turn's model calls its steps) is the host's loop on the kernel (`kernelTurns`, `docs/kernel.md` "The program is the loop"): a session in the journal at the input's `journalAt` (its turns recovered first), the memory, the review's tools, the prompt's prefix sent first at every step and never stored, the tail stored as the conversation's first message, `modelAnswer` and `callTool`. Each part is the host's to swap (`kernelTurns({ model, memory, tools, hostTools, journal })`; the model a layer charging the `ModelSpend` it is given, by default `flatMemory`, `reviewToolHandlers`, no host tools and a `directoryJournal` in the folder `journalAt` names); the port names no folder. It ends when the model answers without a call (or, for a check, once its verdict is recorded: `Judged`; a turn that answers in words is first asked once more, the harvest: the host's note `harvestNote` asks it to report each possible defect it weighed and did not report, the same tools offered, only that answer's `reportFinding` calls run, and its `Answered` summary stays the first answer's, a failed harvest logged; measured on #644's gold group, the turn's summary named the defect and no finding did), or stops with the findings so far at the ledger's refusal, at a failed call, at an answer whose finish is `length` (read from the stream's finish part, since `modelAnswer` keeps no finish reason; the calls that answer asked for run first, so a finding it reported is kept), or when its journal cannot be opened or written (`JournalFailed`, never a failed review). From its start a turn keeps back `TurnOptions.reserve` from its stage (`StageLedger.keepBack`, only when it fits then; `DEFAULT_CLOSING_RESERVE`, $0.10, at most half the find stage, for a review of one turn only: turns beside each other keep nothing back, since three keeping a sixth of the stage each crowd out each other's calls and end refused; a check the same, at most half the verify stage, only when it runs alone: one at a time, or the only one). At its step cap (`DEFAULT_MAX_STEPS`, 16, `--max-steps`), when the ledger refuses a later call while that reserve is held, or, for a check, when it answers in words with no verdict (a verdict in text has no quote to check, so it is never taken), it releases the reserve, stores the host's note (`stepCapNote`) and asks once more with the same tools offered and `tool_choice` left `auto` (measured on the gateway: a narrowed tool list or `none` loses the whole cached prefix), runs only that answer's reporting calls (`reportFinding` in a turn, `verdict` in a check) and keeps its words (`StepCap`'s `summary`), or why it failed (`why`). In any closing call, harvest included, a reporting call the tool refused (a path the pull request does not change, an `endLine` before `line`) is lost unless asked again, so the model is asked once more after one, at most `CLOSING_ASKS` (2) calls in all. The report says `incomplete: <why>` (`INCOMPLETE_BECAUSE`), and `Incomplete: no turn finished.` in place of `No findings.` when no turn answered or reached its step cap.
- Spend: every call is charged to the review's `ModelSpend` ledger through stage ledgers (`stageSpend`): the review's total (`budget.total`, `--max-cost`), inside it the turns' (`budget.find`, `--find-cost`) and the checks' (`budget.verify`, `--verify-cost`), and inside a stage one per turn or check with no cap of its own, so each call's cost is what its own ledger settled while it ran, whatever runs beside it. A stage refuses a reservation that what it settled leaves no room for (`stageStep` `Refuse`, `ModelSpendExceeded` naming the stage's cap), makes one that its open calls crowd out wait, interruptibly and holding nothing, until one closes (`Wait`, decided from the count of open calls, never from a sum of amounts), so parallel calls under a tight cap run one after another instead of failing, refuses one that only what is kept back crowds out, and refuses one that has waited `STAGE_WAIT_MS` (ten minutes) in all, saying so. A hold is closed in the stage whether or not the parent closes it, and what the calls hold is 0 once none is open. `DEFAULT_BUDGET` ($0.80: find $0.50, verify $0.30) is sized from the focused turns' live runs (a group's turn with its 24-call guard and its harvest settled $0.022 to $0.053 on four gold groups: about $0.04 to $0.07 for each of a large pull request's eight or nine groups, the holds growing with every file read whole; a check at 12 calls about $0.02, about twelve with three open at once), first from the single-turn reviewer's (a 16-step turn settles about $0.04, its last request holds about $0.09 at 1 byte a token).
- The model is `openAiCompatibleModel` (`reviewModel`, `DEFAULT_REVIEW_MODEL`: DeepSeek V4.1 Flash through the gateway, Baseten first, 4,096 output tokens a call: at 2,048 a turn's reasoning used 1,925 and another's answer was cut), its key read by the command line from the variable the model names (`VERCEL_API_KEY`) with `Config.Redacted`; another model of the same endpoint with `--model` and its `--price`. Each call's worst case is held at 1 byte a token (`bytesPerToken`), the bound for any tokenizer, since the request is the pull request's text. A call settles at what the gateway billed for it (the `cost` its usage reports), else at its usage at the price: the report's cost is the provider's bill, not an estimate.
- The model's tools (`reviewTools`, `reviewToolHandlers`) read only the clone's objects at the reviewed commit through `Checkout` (`entry`, `blob`, `files`, `grep`), never a folder on disk: only a regular file (mode 100644 or 100755) is read; a symbolic link, a submodule, a folder, a binary file, a missing file and a path that is absolute, holds a `..` or `.` part or a part named `.git` are failed results in words that name what to do. A search that runs past `GREP_TIMEOUT_MS` or writes more than the host keeps, and a git command that fails otherwise, are answered in fixed words (`SEARCH_TOO_LONG`, `SEARCH_TOO_BIG`, `GIT_FAILED`; the last logged whole), never git's own, which may name a host path; exit 128 is a regular expression git refuses (`REGEX_REFUSED`) only when one was asked for. Each tool bounds and pages itself (`READ_LINES_LIMIT`, `SEARCH_LIMIT`, `LIST_LIMIT`, `DIFF_PAGE`); none is sent as a pointer. No answer grows with a line: `readLines` and `readDiff` cut each line at `LINE_SHOWN` with a count and each answer at `PAGE_CHARS`, and `readLines` reads a file's size first (`ls-tree -l`) and refuses one over `READ_FILE_BYTES` in its own words. The tools' git commands run under the host shell's `tool` bound (`TOOL_OUTPUT_BYTES`, 4 MiB), so no call holds more of a command's output; a search reads at most `SEARCH_LIMIT + 1` lines of a file (`--max-count`), says "at least" when a file holds more, runs with `--no-column` and `GREP_CONFIG` (the host's grep config neutralised), and a pattern with a NUL is refused. A search's pattern always follows `-e` and its path `--` (`git grep -F` by default, `-E` on request), so the model's text never reaches an option's place; git's refusal of a regular expression is a failed result. A glob is matched by `globMatches`, never by git or a regular expression, in time linear in the path for each step. Every stage is offered all six tools in one order (`reviewTools`), so their declarations stay in the cached prefix: `reportFinding` takes a claim and evidence of any length, kept cut, never refused (`keptReport`: the claim cut at `CLAIM_LIMIT`, 1,500 characters, with `clipTo`; the evidence's first whole lines within `EVIDENCE_LIMIT`, 1,000, or its one long first line cut, `wholeLinesWithin`, since a quote is checked line by line; measured, 14 of 34 live `reportFinding` calls and 3 of 13 verdicts had been refused for length, 14 of them never sent again), then records in `Findings` under its run and turn in stage `Find`, after `checkedReport` (its path read as a tree path and one the pull request changes and leaves, `endLine` at or after `line`, at most `FINDING_LINES` lines; else a failed result that says what to give, naming at most `CHANGED_NAMED` changed files), and is a failed result in stage `Verify` (`NOT_FINDING_NOW`); `verdict` records a check's first verdict (`Findings.judge`; a later one answers that the first stands; its reason and quote kept as a report's claim and evidence are, `keptVerdict`, at `REASON_LIMIT` and `QUOTE_LIMIT`) in stage `Verify` and is a failed result in stage `Find` (`NOT_CHECKING_NOW`).
- A host adds tools of its own with `kernelTurns({ model, hostTools })`: `HostTools`, a toolkit and its handlers over the turn's `Reviewed` (`(reviewed) => Layer<Tool.HandlersFor<Tools>, never, Checkout | Findings>`, as `reviewToolHandlers` is), typed together, so handlers that lack a tool's or answer the wrong type do not compile; the toolkit is typed both as a `Toolkit` and as what it yields with each tool's own type (`OwnTools`), which a toolkit of `Toolkit.make` or `Toolkit.merge` is, and none of its tools may take a name of the six (`NoStockNames`, a compile error, a toolkit keyed by any string refused too: `Toolkit.merge` lets a later tool replace an earlier one; there is no check at run time). Every request of every finder turn and check offers the six in their order, then the host's (`Toolkit.merge(reviewTools, host.toolkit)`); with no host tools it offers `Toolkit.empty` after them, every request's declarations byte for byte the six's alone. A call in a step whose name the host's toolkit has (`Object.hasOwn`) runs through `callTool` over the host's toolkit, any other through the six's (an unknown name fails there as before); the closing call and the harvest run only the reporting tool, and only `readLines` and `readDiff` count as opening a file. What a host's tools need beyond their handlers (`HostToolNeeds`: what they declare and what their parameters' schemas need to be sent; `never` for plain tools) is in the layer's requirements. Calls are run by two toolkits, not one merged one, because `callTool` needs its toolkit's own type (`OwnTools`), which a merge inside `kernelTurns`, generic over the host's tools, cannot show. A host tool's description and parameters are the host's text the model reads: they are not in `REVIEW_TOOLS_VERSION` (the six's) and are the host's to pin and version. `ReviewTurns.hostTools` (`HostToolsOffered`) says what each request offers beyond the six: the names in order, which `review.json` keeps as `hostTools` (none for the six alone), so runs with and without an add-on are told apart, and the bytes the declarations add as the reviewer's wire sends them (`declarationBytes`, the request's bytes with them less without, exactly), which a group's first call's hold counts (`firstCallHold(prompt, price, declarationBytes)`; 0, the hold unchanged, with none). A host tool's handler that fails, as data (`failureMode: "return"`) or as an error, or dies, is stored by `callTool` as a failed result the model reads and the turn goes on: `kept` maps only a failure to store it to `JournalFailed`. Its handlers layer is built for every turn and check (with the turn's `Reviewed`), so a long-lived resource (a language server, a connection) belongs in a service the tool declares in its `dependencies`, which the host provides once to `kernelTurns`' layer (`HostToolNeeds`), never in the handlers layer; and a host tool bounds and pages its own answer as the six do (no answer that grows with a file or a repository), since every result it gives is sent in every later request of the turn. The command line offers the six alone: a host that adds tools composes the review itself, as `reviewCli` does (its `reviewLayers` is not exported): the forge, the checkout and the logs from the exported adapters (`ghForge`, `gitCheckout`, `directoryLogs` over `hostShell`), `findingsInMemory` and a `ModelSpend` ledger, its own `kernelTurns({ model, verifyModel, hostTools })` over them, and `reviewPullRequest`.
- The prompt is a pure function of the prepared review: its prefix (`reviewPrefix`: the system text, then one message holding the instruction files, the title and description, the packed diff and the CI's digest, each `framed` and clipped) holds no date, sha or number of the run and nothing of a turn's or a check's, so it stays byte-stable within a pull request and a provider's cache keeps it across steps, turns and checks; a turn's tail (`reviewPrompt`) is its finder's words (`FIND_TAIL`) and the order to walk the files in, each path framed (`changed-files`), one a line through `shownPath` after `in the diff: ` or `left out: `; a focused turn's (`focusPrompt`) is `FOCUS_TAIL` of its finder alone; a check's (`verifyPrompt`) is `VERIFY_TAIL` and the finding framed (`reported-problem`). The instruction files are shown nearest the changed paths first (`nearestFirst`: the deepest folder, then the one holding more changed paths), each whole while those shown whole stay within `RULES_WHOLE` (16,000 characters), else its headings (at most `RULE_HEADINGS_SHOWN`) and `HEADINGS_NOTE`, and past `RULES_SHOWN` (24,000) named. A change to its words is a new `REVIEW_PROMPT`; a change to a tool's is a new `REVIEW_TOOLS_VERSION`.
- `--at first` reviews the commit of the head branch's earliest `pull_request` CI run started while the pull request was open (`firstHeadOf`, over the runs and the pull request's timeline, `TIMELINE_QUERY`: GitHub empties a merged pull request's runs' `pull_requests`, and a force-push drops the first head from the commit list but never from the runs); with no such run, the head its first force-push replaced; else its oldest commit; `at.source` and `AT_SOURCE_WORDS` say which, and what a fallback may miss. The commit is fetched by its sha when the head's ref no longer reaches it. Any commit but the head (`--at first` or a sha, even when it is the head) is reviewed against where its history meets the pull request's base (`mergeBase`): its diff, its `.gitattributes` and its rules from there, its CI from its own runs, and the description as it stood when it was committed (`Forge.descriptionHistory`, `DESCRIPTION_QUERY`: the commit's time and the description's saved versions, its sha sent with `-f`, since `-F` reads a sha of digits as a number; `descriptionAsOf`: the last version saved by then, else the one it was opened with; the current one when it was never edited, a commit the forge does not know, or every version read is later and the history holds more than `DESCRIPTION_EDITS_READ`), since a description edited later often lists the fixes made after the commit (seven of the review eval's twenty pull requests); and its prepared review records `later`, the head now and the paths `<reviewed>...<head>` changes (`changedPaths`), for scoring against later fixes.
- Each run of a review has a folder of its own, `<number>/<sha>/<run>/`, the run named by when it started (`runNameOf`), so a rerun never writes over one before it. It keeps the prepared review (`prepared.json`), each turn's and check's journal (`turn-N/`, `check-N/`) and the report (`review.json`: the run, the prompt's and the tool set's versions, the host's tools offered after the six (`hostTools`, by name), the model, the finder, whether the vote and the checks ran, how many turns were asked for (`turnsAsked`), every finding with its turn, every bucket with its votes and why it was kept or not, every check with the finding it was shown and its verdict, whether its quote held and its outcome, each turn's and check's session, each call's tokens, cached tokens and cost, and each stage's totals), for offline scoring.
- Tests never reach a network: the forge is a stub `HostShell`; git runs on a fixture repository made in a temporary folder (`git-fixture.testing.ts`) with a generic identity and `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`.

## The sandbox

A pull request's commands (`--run`, and the profile with `--validate`) run in bubblewrap (`bwrap-shell.adapter.ts`, `validate.usecase.ts`).

- **What runs with the network: only the package manager, only for a trusted base.** A base is trusted when it is in the history of the repository's default branch as the forge names it (`Forge.defaultBranch`) and the remote has it now (`Checkout.onBranch`), checked first by `validate` itself, so no caller of `sandboxValidations` can skip it; any other base is `Refused`: no install, no snapshot, no verdict written. That base's install is the one command that shares the host's network namespace, so every service on the host's `localhost` (a database, a dashboard) is reachable from it; it runs the host's package manager with no script of the repository's (`--ignore-scripts`, `--ignore-pnpmfile`, yarn berry's `--mode=skip-build`), but the manager still reads the base's own config (`.npmrc`, `bunfig.toml`, `.yarnrc.yml`) and fetches what its lockfile names. A pull request's head never installs and never has the network.
- **The head restores the base's install.** It is validated only when every file an install reads (`isDependencyPath`: every lockfile and `package.json`, `bunfig.toml`, `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `pnpm-workspace.yaml`, `.pnpmfile.cjs`, and every file in a `patches` folder) is byte for byte the base's (`dependencyPaths`, `sameFiles`), and none of them is a link or a submodule at either end (`Checkout.notRegular`); otherwise nothing runs: "dependencies changed: not validated locally (CI covers it)". The base's `node_modules`, saved inside the sandbox right after its install (before any of its checks runs), is kept as a snapshot under the base's commit, the dependency files and the manager's version, and the head's clone restores it in a sandbox with no network and no cache bound.
- **The clone.** Each run (the base's, then the head's) gets a clone of its own from the bare clone (`git clone --no-hardlinks --no-checkout`, no template), checked out by host git before any sandbox runs with no filter driver at all: no attributes file of the host's (`core.attributesFile=/dev/null`, `GIT_ATTR_NOSYSTEM=1`), and every driver the host's config defines (`git config --get-regexp '^filter\.'`, git-crypt, lfs, a custom smudge) turned off by `neutralFilters`, so a `.gitattributes` the head commits can name none. Once a sandbox has written to it, its `.git` (config, hooks) is the pull request's: no host git command runs in it again, and it is deleted with `rm` when its scope closes.
- **The bot's commands never run the repository's programs.** The install, a snapshot saved or restored and the version asked run with `HELPER_PATH` (`/opt/tool/bin:/usr/bin:/bin`, no folder of the clone's) and name every program by its absolute path (`/opt/tool/bin/bun`, `/usr/bin/cp`), so a `node_modules/.bin/bun` the pull request commits is never run in their place. Only the repository's own checks get `CHECK_PATH`, its `node_modules/.bin` first: they run its code by design, offline. npm and pnpm install with `npm_config_ignore_scripts=true`, `npm_config_git=/usr/bin/git` and `npm_config_userconfig=/dev/null`, which a project's `.npmrc` cannot override; yarn classic with `YARN_IGNORE_PATH=1` (a `.yarnrc`'s `yarn-path` is not run).
- **`bwrap`** is spawned directly with an argv (never through a host shell) and an empty environment: started with the host's, its own first process inside would keep it in `/proc/1/environ`. `--unshare-all` (user, pid, network, ipc, uts, cgroup), `--die-with-parent`, `--new-session`, `--clearenv` with a fixed `PATH` (`HELPER_PATH` or `CHECK_PATH`, above) and `HOME=/tmp/home` (`INNER_HOME`: in the sandbox's own tmpfs, so a tool's home cache never lands in the clone; bun's transpiler cache there dirtied the tree and tripped a repository's own gates); `/usr` and the system's top folders read-only (a merged `/usr` link made again as a link); of `/etc` only the linker's cache and alternatives, and with the network the resolver's files and certificates; a fresh `/proc`, `/dev`, and `/tmp`, a tmpfs held in memory, bounded at 2 GiB (`Limits.tmpBytes`) where the host's bwrap has `--size` (0.10 and later; Ubuntu 24.04's 0.9 does not, so there it is unbounded); the clone at `/work`, the only writable bind but a package cache during an install and a snapshot folder while one is saved. The command is `/bin/sh`'s `$1`, started by the launcher (`LAUNCHER`, `/usr/bin/bash`, which the host must have) after it closes every inherited descriptor but the three streams (Bun spawns without close-on-exec, so its open files reached the sandbox; bash, since dash, Ubuntu's `/bin/sh`, reads `exec 10>&-` as a program named `10` and exits 127) and `ulimit` sets no core files and the largest file (2 GiB); the address space only when a host sets `Limits.memoryBytes` (bun reserves far more than it uses: efferent's type check dies under 8 GiB).
- **The toolchain** (`bun`, `node` with npm and npx, `pnpm`, `yarn`) is found on the host's `PATH` by real path and bound read-only under `/opt/tool/<name>`, the least each needs: a program under `/usr` only linked; `node` by its program file and npm's package (`lib/node_modules/npm`), never its installation folder; a program in a package by the package; a shim with a `.tools` folder (pnpm's) by the two; anything else by its file alone. A folder in a home that is not a package's (`/node_modules/`) or a `.tools` is refused, and the tool with it. The host's `PATH` is never passed.
- **The cache.** The base's install writes the bot's own package cache (`<cache>/<owner>/<repo>/packages/<manager>/`, bound at `/cache`), packages copied, never hard-linked, never the host's own cache; no sandbox of a head binds it.
- **Managers.** From the base's lockfile (the one `packageManager` names, else the first of `LOCKFILES`): bun, npm (through node), pnpm (`--ignore-pnpmfile`: `--ignore-scripts` alone still loads `.pnpmfile.cjs`; and in every sandbox `npm_config_manage_package_manager_versions=false`, `INNER_ENV`, so pnpm runs as the host has it and never fetches the repository's version), yarn v1 through the host's yarn; a yarn berry repository only through the base's `yarnPath`, normalised (`normalPath`), inside the repository and of letters, digits, `.`, `_`, `/` and `-` alone, and only when the pull request changes none of it, `.yarnrc.yml`, a file `.yarnrc.yml` names (`yarnrcPathsOf`), `.yarn/plugins/` and `.yarn/releases/` (corepack is never run). Otherwise `Refused`, with the reason. Checked by hand in the sandbox on zero-dependency fixtures: bun, npm and pnpm install with no `postinstall` run and pnpm with no pnpmfile loaded; yarn is not, since this host has none.
- **The profile** (`profileOf`, no model): the commands in the fenced blocks under the base instruction files' "definition of done" heading, then the check scripts of the base's `package.json` (`CHECK_SCRIPTS`), then `--run`'s; each kept only when it has no shell syntax and names a known tool (`tsc`, `npx tsc`, `bunx tsc`, `bun test`, `turbo run <task>`) or a script of the root `package.json` (`droppedBecause`). A profile command runs on the head only once it exited 0 on the base; each verdict, a pass, a failure or a timeout, is kept by the base's commit and the command (`ReviewCache.verdict`), so every new base asks again. A command given by hand is not asked on the base.
- **Time.** Each command has five minutes (`VALIDATION_TIMES.commandTimeoutMs`), each clone's run fifteen for its install and its commands together (`budgetMs`); what the budget leaves no time for is `unrun` with the reason, and on the base it is dropped from the profile. A run that ends, however, kills the sandbox's process group; the pid namespace takes every process in it, one that called `setsid` too.
- **What it does not guarantee.** A kernel exploit escapes any namespace sandbox. CPU and memory exhaustion are bounded only by the timeout (no cgroup, and no `ulimit -v` by default, since it is no memory bound for bun: memory needs `systemd-run --user -p MemoryMax=` or a container; a fork bomb runs until the timeout, under the host user's process limit). During the base's install the host's network namespace is shared, so local services (a database, a dashboard on `localhost`) are reachable from the package manager, which reads the base's registry config: the base is the default branch's, merged code, never the pull request's. The bot's package cache is shared by every review of a repository: what a registry served into it is read by later base installs, never by the host's.
- **The isolation probe** (`bwrap-shell.adapter.test.ts`) runs bwrap for real: it skips where bwrap or user namespaces are missing, but never in CI (`CI` set), whose workflow installs bubblewrap and allows unprivileged user namespaces (`kernel.apparmor_restrict_unprivileged_userns=0` on Ubuntu 24.04).
