# @xandreed/review

`efferent-review`, a pull request reviewer built on the kernel: it reads a pull request from its forge, its diff, the repository's rules and its CI, prepares them for a review, and reviews it with a model. `efferent-review prepare <number> --repo <owner/name>` prints what a review is given, asking no model; `efferent-review review <number> --repo <owner/name>` runs one pass of the model over it and prints the report. Node 24 (the declared engine; the tests run on Bun): the package is not built, so the bin, `bin/efferent-review.mjs`, loads `src/main.ts` through `tsx`; layer `review` in `foundry.config.ts` (imports `@xandreed/core`, `@xandreed/sdk`, `@xandreed/sdk/node`, `effect/ai` and `node:` only). Private: it is gated like every package, but it is in neither the build's `names` nor `CURATED_ENTRIES`, and Changesets ignores it (`.changeset/config.json`, `ignoredNames` in `scripts/release-version-plan.ts`), so no release publishes it.

## Rules

- The orchestration is code, never a model: fetching, filtering, packing, running and digesting are pure functions with table tests (`*.entity.functions.ts`) or adapters behind a port.
- Every host command whose output is parsed (`gh … --json`, `gh api`, `git diff`, `git ls-tree`, `git cat-file`, `gh run view --log-failed`) is read whole through `runWhole`: the host's shell keeps `HOST_OUTPUT_BYTES` of each stream, and an output it cut fails with `OutputCut`, never parsed. An exit code the caller did not allow is `CommandFailed`.
- Every argument of a host command is quoted (`commandLine`): a path, a branch or a title from a pull request is data, never shell.
- A pull request's rules are read at its base commit (`show` at `base.sha`), so it cannot rewrite the rules it is reviewed by; a link (`CLAUDE.md` → `AGENTS.md`) is not read twice.
- `gh` and `git` run on the host's shell with the host's environment (`gh` reads its login there). Nothing of the pull request's runs on the host: a process of the host's user can read the parent's environment (`/proc/<pid>/environ`), the host's credentials and the shared clone, whatever variables it is given, so trimming the environment is no isolation. A pull request's commands run only through `Validations` over a `Shell` the host provides, which must be a sandbox; none ships, so the command line provides no `Validations` and has no `--run`. With one given, `prepareReview` runs `PrepareOptions.run` only for a head in the base repository whose author may write to it (`admin`, `maintain` or `write`), under `allowOnly` (a guard on which commands run, not isolation). CI's failed logs are the validation source.
- Every host-side git command is built by `gitArgv`: `core.hooksPath=/dev/null` (no hook of the clone's runs), `core.fsmonitor=false`, `protocol.allow=never` with only the transports given allowed (`https` by default), and `--literal-pathspecs` (a folder named `:(glob)x` or `:!x` is a name).
- Clones live under a cache root outside every git repository (`~/.efferent-review/<owner>/<repo>/` by default; `CacheRootRefused` otherwise): a bare clone in `mirror.git`, worktrees in `worktrees/`, removed when their scope closes, logs and a review's records in `reviews/<number>-<sha12>/` (the commit under review).
- CI runs are every run for the head's sha started by `pull_request`, `push`, `merge_group` or `pull_request_target` (`CI_EVENTS`), every page of runs and of jobs read (`gh api --paginate --slurp`); a run with no job is not listed. A failed log the forge no longer has is `NoLog`; one it refuses (auth, a repository 404) is that run's `Unavailable` entry, stripped and cut, and fails nothing else.
- Everything a log, a path or a title holds is the pull request's text. A digest strips escape sequences and control characters, cuts each line with the kernel's `clipTo` and bounds its failures and summary; a path is shown through `shownPath` (a JSON string when it holds a control character, a quote or a backslash), so a name cannot forge a line and maps back to one file.
- Which files the model reads: lockfiles, files the base's `.gitattributes` marks generated or vendored (a folder's name drops nothing), binary and deleted files are left out, each named in a line with its counts (a lockfile with whether a manifest changed too); a file that only loses lines is kept. The rest is packed manifests, CI files and small config first, then code largest first, then large config, then docs.
- Every policy is swappable: `prepareReview(repo, number, options, policies)` takes `ReviewPolicies` (`verdict`, `pack`, `rulesAlong`, `digest`, `mayRun`, `failed`), `STOCK_POLICIES` by default; the head is fetched by the ref the forge serves it under (`fetchRef`).
- A review's pass is the host's loop on the kernel (`kernelPasses`, `docs/kernel.md` "The program is the loop"): a session in a `directoryJournal` of its own under the review's folder (`<number>-<sha12>/pass-<n>/`, its turns recovered first), plain `flatMemory`, the prompt's prefix sent first at every step and never stored, the pass's tail stored as the conversation's first message, `modelAnswer` and `callTool`. A pass ends when the model answers without a call, or stops with the findings so far at its step cap (`DEFAULT_MAX_STEPS`, 16), at the ledger's refusal, at a failed call, or at an answer whose finish is `length` (read from the stream's finish part, since `modelAnswer` keeps no finish reason); the report says `incomplete: <why>` (`INCOMPLETE_BECAUSE`). A call's cost is what the ledger settled while it ran, so passes run one after another.
- The model is `openAiCompatibleModel` (`reviewModel`, `DEFAULT_REVIEW_MODEL`: DeepSeek V4.1 Flash through the gateway, Baseten first, 2,048 output tokens a call), its key read by the command line from the variable the model names (`VERCEL_API_KEY`) with `Config.Redacted`, every call charged to one `ModelSpend` ledger per review capped at `--max-cost` (`DEFAULT_MAX_COST`, $0.15). The worst case is held at 2 bytes a token (`bytesPerToken`): at 1, a late step's hold alone (a ~140 KB request) would take a normal review past its cap.
- The model's tools (`reviewTools`, `reviewToolHandlers`) read only the clone's objects at the reviewed commit through `Checkout` (`entry`, `blob`, `files`, `grep`), never a folder on disk: only a regular file (mode 100644 or 100755) is read; a symbolic link, a submodule, a folder, a binary file, a missing file and a path that is absolute, holds a `..` or `.` part or a part named `.git` are failed results in words that name what to do. Each tool bounds and pages itself (`READ_LINES_LIMIT`, `SEARCH_LIMIT`, `LIST_LIMIT`, `DIFF_PAGE`); none is sent as a pointer. A search's pattern always follows `-e` and its path `--` (`git grep -F` by default, `-E` on request), so the model's text never reaches an option's place; git's refusal of a regular expression is a failed result. A glob is matched by `globMatches`, never by git or a regular expression, in time linear in the path for each step. `reportFinding` records in `Findings`; the host checks nothing it reports yet.
- The prompt (`reviewPrompt`, `REVIEW_PROMPT`) is a pure function of the prepared review: its prefix (the system text, then one message holding the instruction files, the title and description, the packed diff and the CI's digest, each `framed` and clipped) holds no date, sha or number of the run, so it stays byte-stable within a pull request and a provider's cache keeps it across steps and passes; the tail names the order to walk the files in. A change to its words is a new `REVIEW_PROMPT`; a change to a tool's is a new `REVIEW_TOOLS_VERSION`.
- `--at first` reviews the commit the pull request's earliest `pull_request` CI run tested (`firstHeadOf`: runs of the head branch matched by the commit they tested, since GitHub empties a merged pull request's runs' `pull_requests`), else its first commit, said in `at.source`. A commit other than the head is reviewed against where its history meets the pull request's base (`mergeBase`): its diff, its `.gitattributes` and its rules from there, its CI from its own runs.
- Each review keeps, under its folder, the prepared review (`prepared.json`), the report (`review.json`: the prompt's and the tool set's versions, the model, every finding with its pass, each call's tokens, cached tokens and cost) and the pass's journal, for offline scoring.
- Tests never reach a network: the forge is a stub `HostShell`; git runs on a fixture repository made in a temporary folder (`git-fixture.testing.ts`) with a generic identity and `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`.

## Public surface

The package is not published; `src/index.ts` names what later steps (several passes, a vote, verification) build on: `reviewPullRequest` with `ReviewOptions`; `reviewPrompt`, `REVIEW_PROMPT`, `REVIEW_SYSTEM`; the tools `reviewTools` (`ReadLines`, `SearchCode`, `ListFiles`, `ReadDiff`, `ReportFinding`) and `reviewToolHandlers` over `Reviewed`, `REVIEW_TOOLS_VERSION`; the ports `Findings` (`findingsInMemory`) and `ReviewPasses` (`kernelPasses`, `PassInput`, `PassResult`, `PassEnded`, `DEFAULT_MAX_STEPS`); `reviewModel`, `ReviewModel`, `DEFAULT_REVIEW_MODEL`, `DEFAULT_MAX_COST`; `reviewReport`, `reportText`, `ReviewReport`; `ReviewAt`, `ReviewedAt`, `AT_SOURCE_WORDS`, `firstHeadOf`; `Finding`, `FindingReport`, `PassNumber`; and, from the preparation, `prepareReview` with `PrepareOptions`, `PreparedReview`, `ReviewPolicies`, `STOCK_POLICIES` and `summaryText`; the pure parts (`parseUnifiedDiff`, `renderDiff`, `shownPath`, `fileVerdict`, `attributesOf`, `packDiff`, `droppedLines`, `rulesAlong`, `digestLog`, `plainText`, `gitArgv`); the ports `Forge`, `Checkout`, `Validations`, `ReviewLogs`, `HostShell`; and their adapters `ghForge`, `gitCheckout`, `shellValidations` (`allowOnly`), `directoryLogs`, `hostShell` (`runWhole`), and `reviewCli`.
