The kernel, a small core with every other part a plain Effect layer, ships as two new entries beside the existing engine, which neither imports nor is imported by it. `@xandreed/core/kernel` holds what every agent has, whatever its workflow: ids, `Message`, the event envelope with its tags, the conversation's records (`conversation.user.message`, `conversation.assistant.message` with the tool calls the model made, and `conversation.tool.result`, written with `userMessage`, `assistantMessage` and `toolResult`), the `JournalStorage` and `Sessions` contracts with a conformance kit each, reading a journal, `inspectionOf`, and `Core`, which is events only (`publish`, `on` and `events`), with `kernel({ capacity? })`, the layer that provides it. `@xandreed/sdk/kernel` holds the workflow contracts, each in a contract folder, with a kit where a plugin can break the contract's rules (the memory's, the summarizer's; memory's `Memory`, one function, `context(session)`, which keeps nothing and returns the messages that follow the system text; the inbox's `Inbox`; what the UI shows: a view record tagged `ui` that no memory sends, and `viewsOf`, the fold a client draws), and the stock plugins `inProcessJournal`, `sessions`, `flatMemory`, `windowMemory`, `summaryMemory` (old turns folded into a summary stored once, over a `Summarizer` the host provides) and `inbox(turn)`, each a layer whose type says what it needs, with `scriptedModel`, a `LanguageModel` that follows a script and calls no provider. There is no loop: the host's program is the loop. A turn opens with `sessions.open(id)`, stores the user's message, asks memory for the context, calls Effect AI's `LanguageModel` with the system text first, and stores the answer; the journal holds the conversation and never the system text or a request. A turn that uses tools is a loop the host writes: it offers Effect AI's `Toolkit` to the model, runs each call through the toolkit's handlers, stores the call and its result (a failure as a failed result, and the turn goes on), and asks again; the kernel adds no tool service, and tool definitions are code, never stored. Every memory sends its messages through `paired`, so no call goes without its result, and the memory kit checks it (`pairs`). A plugin of a host's own takes part by hooking events with `Core.on` or by wrapping a contract: a wrapper of `Memory` (a higher-order plugin, given the memory it wraps) adds what one request needs after the context, whole and in its order, and stores none of it, which `memoryWrapperConformance` checks (`starts-with-inner`, `own-records`). A loop's two blocks are functions that each store what they produce: `modelAnswer` reads one call's answer from the model's stream and stores it with its tool calls and its usage, and `callTool` runs one call and stores its result. Both give the work its turn as `CurrentTurn`, which a tool declares in `dependencies`, so a tool can append a record of its own, publish its progress or start a helper under its caller. A plugin imports contracts and core, never another plugin. A host provides the layers to its program, or composes them with `Layer.provideMerge`, and a stack whose type is written out does not compile when a part is missing. The inbox queues messages per session and answers them in order with the host's turn, each in a turn of its own. An event is named by the owner of the contract that defines it (`core.session.turn.started`, `plugin.window.dropped`), the conversation's under `conversation.`, and the set is open: a plugin defines its own with `storedEvent` and `liveEvent`, declaring the tags that say what it is for. It is a first cut, with journals kept in the process, and it will change as the parts it leaves out return; `docs/kernel.md` is its direction document, and `docs/adr/0002-core-owns-state-plugins-own-workflows.md`, `docs/adr/0003-journal-holds-the-conversation.md` `docs/adr/0004-tool-traffic-is-conversation.md`, `docs/adr/0005-context-for-one-request.md`, `docs/adr/0006-a-sub-agent-is-a-session.md` `docs/adr/0007-a-tool-reaches-its-turn.md`, `docs/adr/0008-a-memory-keeps-its-summary.md` and `docs/adr/0009-what-the-ui-shows-is-a-record.md` record where core ends, what the journal holds and how tool calls are stored and sent. Neither entry imports a `node:` or `bun:` module.
